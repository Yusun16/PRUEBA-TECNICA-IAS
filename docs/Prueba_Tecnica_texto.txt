Incidente N3: conciliación segura de pagos con reintentos e inconsistencias de datos
Tiempo máximo
2 horas
Modalidad
Candidato externo
Entrega
Repositorio Git
Objetivo del ejercicio
Resolver un incidente productivo acotado y dejar una corrección ejecutable, verificable y operable. Se 
busca observar cómo analiza evidencia, toma decisiones, implementa, prueba y deja trazabilidad técnica 
bajo una restricción realista de tiempo.
1. Contexto de negocio
PagoClaro 
procesa pagos para comercios. El equipo de operaciones detectó que, después de una 
degradación del proveedor externo de pagos, algunos pagos quedaron con estados inconsistentes o con 
movimientos contables duplicados. El incidente fue escalado a soporte N3 porque los reintentos manuales 
ya no son seguros: una nueva ejecución puede agravar la inconsistencia.

Un pago confirmado debe terminar con un único débito neto por el valor del pago.

Los movimientos contables son inmutables: no se eliminan ni se actualizan; una corrección se 
representa mediante un movimiento de reverso relacionado con el movimiento que corrige.

Cuando la evidencia del proveedor es contradictoria o insuficiente, el sistema no debe adivinar el 
resultado: debe conservar los datos y señalar el caso para revisión manual.

La misma solicitud de conciliación puede repetirse por error operativo o por un reintento técnico. 
Repetirla no debe generar efectos contables ni registros de auditoría duplicados.

Dos solicitudes sobre el mismo pago pueden llegar casi al mismo tiempo. El resultado debe conservar 
consistencia.

La operación debe dejar trazabilidad suficiente para soporte sin registrar secretos ni datos sensibles 
innecesarios.

PAYMENT(
  id NUMBER PRIMARY KEY,
  external_ref VARCHAR2(40) UNIQUE NOT NULL,
  status VARCHAR2(20) NOT NULL,            -- PENDING | CONFIRMED | REJECTED
  amount NUMBER(18,2) NOT NULL,
  updated_at TIMESTAMP NOT NULL,
  row_version NUMBER DEFAULT 0 NOT NULL
)
PROVIDER_EVENT(
  id NUMBER PRIMARY KEY,
  payment_id NUMBER NOT NULL REFERENCES PAYMENT(id),
  provider_event_id VARCHAR2(60) UNIQUE NOT NULL,
  provider_status VARCHAR2(20) NOT NULL,   -- APPROVED | DECLINED
  received_at TIMESTAMP NOT NULL
)
LEDGER_ENTRY(
  id NUMBER PRIMARY KEY,
  payment_id NUMBER NOT NULL REFERENCES PAYMENT(id),
  entry_type VARCHAR2(20) NOT NULL,        -- DEBIT | REVERSAL
  amount NUMBER(18,2) NOT NULL,
  related_entry_id NUMBER NULL REFERENCES LEDGER_ENTRY(id),
  created_at TIMESTAMP NOT NULL
)
SUPPORT_AUDIT(
  id NUMBER PRIMARY KEY,
  payment_id NUMBER NOT NULL REFERENCES PAYMENT(id),
  action VARCHAR2(40) NOT NULL,
  reason VARCHAR2(400) NOT NULL,
  created_at TIMESTAMP NOT NULL
)

3. Reto
Implemente una solución mínima en Java con Spring Boot 
que permita a soporte N3 conciliar un pago 
por su referencia externa a partir de la evidencia disponible en base de datos. La solución debe ser 
ejecutable o, si usa dependencias externas que no estén disponibles, debe dejar claramente documentado 
cómo ejecutarla y validar sus partes principales.

3.1 Comportamiento funcional esperado
1.
Exponer una operación de soporte que reciba la referencia externa de un pago y determine su situación
 
usando PAYMENT, PROVIDER_EVENT y LEDGER_ENTRY.
2.
Para casos con evidencia suficiente, aplicar únicamente las correcciones necesarias para dejar el pago 
consistente con las reglas de negocio. Los movimientos contables existentes no se borran ni se 
modifican.
3.
Cuando exista evidencia contradictoria o no sea posible decidir con seguridad, no aplicar cambios 
destructivos ni compensaciones; devolver un resultado que indique revisión manual y el motivo.
4.
Una repetición de la misma conciliación sobre un caso ya resuelto no debe generar nuevos efectos 
equivalentes.
5.
Dos ejecuciones cercanas sobre el mismo pago no deben dejar el ledger o el estado del pago en una 
situación inválida.
6.
Registrar información útil para diagnóstico y auditoría, evitando exponer información sensible o detalles 
internos innecesarios en la respuesta de la API.
3.2 Artefactos de base de datos

Entregue una consulta SQL que permita detectar, para las últimas 24 horas, pagos con una diferencia 
entre el monto esperado y el débito neto, o con estado incompatible con la evidencia del proveedor. La 
consulta debe ser legible y justificable.

Entregue un procedimiento o bloque PL/SQL invocable que realice de forma atómica una acción de 
conciliación segura para un pago, o que registre que el caso requiere revisión. Defina la interfaz que 
considere adecuada y documente las condiciones bajo las cuales modifica datos.

Si propone índices, restricciones o cambios al esquema, entréguelos como scripts separados y explique
 
brevemente su propósito. No es obligatorio modificar el esquema.
3.3 Pruebas

Incluya pruebas automatizadas para el comportamiento principal y al menos dos condiciones de borde o
 
error que considere relevantes.

Debe existir evidencia verificable de que una repetición de la operación no duplica efectos.

Cuando una prueba dependa de Oracle o de infraestructura no disponible durante la evaluación, puede 
aislarla o documentar una estrategia de validación reproducible.
4. Análisis y decisiones
No se espera certeza artificial
El material del incidente contiene vacíos deliberados. Si una decisión depende de información no 
disponible, documente el supuesto, el riesgo de ese supuesto y qué comprobaría en producción antes de 
aplicar la corrección.

Deje un diagnóstico breve que separe: hechos observados, hipótesis de causa, validaciones que haría y
 
corrección propuesta.

Registre las decisiones técnicas relevantes: contexto, alternativas consideradas, decisión, trade-offs, 
riesgos y cómo verificó el resultado. Puede hacerlo en README, ADRs u otro formato claro.

Incluya una nota operativa corta para soporte: cómo identificar un caso seguro de conciliar, cuándo 
detenerse y qué evidencia revisar después de ejecutar la solución.
